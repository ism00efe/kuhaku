# Sessions

A multi-turn conversation needs memory: what the user said earlier, and what each tool
worked out so far. `kuhaku.core.session` keeps that state for you, for any tool, instead
of passing `history=` and `prior=` back in by hand on every call.

- A `Session` holds one conversation: its `messages`, per-tool `state`, `metadata`, and
  the identity that owns it.
- A `SessionStore` persists sessions: `InMemorySessionStore` (process-local) or
  `SQLiteSessionStore` (one file, standard library only).
- `ContextWindow` picks which messages go into the next LLM call: the last N turns and a
  token budget.

## Creating, saving and loading

Every store call takes the caller's `AuthContext`. A session belongs to the identity
that created it.

```python
from kuhaku.core.auth import AuthContext
from kuhaku.core.models import Message
from kuhaku.core.session import InMemorySessionStore

store = InMemorySessionStore(default_ttl_seconds=3600)
alice = AuthContext("alice", is_authenticated=True)

session = store.create(alice, metadata={"channel": "web"})
session.append(Message.user("I'd like some tea"))
session.tool_state("my_tool")["step"] = 1
store.save(session, alice)

loaded = store.get(session.id, alice)
print(loaded.messages[0].text)        # "I'd like some tea"
print(loaded.state)                   # {'my_tool': {'step': 1}}
```

A loaded `Session` is a working copy: nothing is stored until `save`. Tool state is
namespaced (`session.tool_state("extraction")`), so two tools sharing one conversation
never overwrite each other. Everything in `state` and `metadata` must be
JSON-serializable; anything else fails at `save`, not later.

For persistence across processes use the SQLite backend:

```python
import tempfile
from pathlib import Path

from kuhaku.core.auth import AuthContext
from kuhaku.core.models import Message
from kuhaku.core.session import SQLiteSessionStore

path = Path(tempfile.mkdtemp()) / "sessions.sqlite3"
alice = AuthContext("alice", is_authenticated=True)

session = SQLiteSessionStore(path).create(alice)
session.append(Message.user("hello"))
SQLiteSessionStore(path).save(session, alice)

print(SQLiteSessionStore(path).get(session.id, alice).messages[0].text)  # "hello"
```

The database file is created on first use, not when the store is constructed.

## Ownership

Loading, saving or deleting a session with a different `AuthContext` fails exactly like
a session that does not exist: `SessionNotFound`, with the same message. A caller cannot
tell "not yours" from "not there", the same rule RAG applies to documents.

```python
from kuhaku.core.auth import AuthContext
from kuhaku.core.session import InMemorySessionStore, SessionNotFound

store = InMemorySessionStore()
alice = AuthContext("alice", is_authenticated=True)
bob = AuthContext("bob", is_authenticated=True)

session = store.create(alice)
try:
    store.get(session.id, bob)
except SessionNotFound as exc:
    print(exc)                         # No session '...' was found.
```

The owner is the pair (`identity`, `is_authenticated`): an unauthenticated context
claiming the identity `"alice"` does not own Alice's sessions. Anonymous contexts can own
sessions too; any anonymous caller holding such a session's id can load it. Session ids
are always generated by the store (144 random bits), never chosen by the caller.

## Concurrent turns

Each save checks the version the session had when it was loaded. If another save landed
in between, the second one raises `SessionConflict` instead of silently overwriting the
first turn. Reload and redo the turn:

```python
from kuhaku.core.auth import AuthContext
from kuhaku.core.models import Message
from kuhaku.core.session import InMemorySessionStore, SessionConflict

store = InMemorySessionStore()
alice = AuthContext("alice", is_authenticated=True)
session = store.create(alice)

first = store.get(session.id, alice)
second = store.get(session.id, alice)
first.append(Message.user("turn one"))
store.save(first, alice)

second.append(Message.user("turn two"))
try:
    store.save(second, alice)
except SessionConflict:
    retry = store.get(session.id, alice)
    retry.append(Message.user("turn two"))
    store.save(retry, alice)

print([m.text for m in store.get(session.id, alice).messages])  # ['turn one', 'turn two']
```

With the SQLite backend the check is one atomic `UPDATE ... WHERE version = ?`, so it
holds across threads and across processes sharing the file.

## The message window

A turn starts at a `user` message and runs until the next one, so a reply is never
separated from what it answers. Leading `system` messages are kept.

```python
from kuhaku.core.models import Message
from kuhaku.core.session import ContextWindow, last_turns, within_token_budget

messages = [Message.system("Be brief.")]
for i in range(6):
    messages += [Message.user(f"question {i}"), Message.assistant(f"answer {i}")]

print(len(last_turns(messages, 2)))                    # 5: system + two turns
print(len(within_token_budget(messages, 30)))          # newest turns that fit 30 tokens
window = ContextWindow(max_turns=4, max_tokens=60)     # both limits at once
print([m.text for m in window.apply(messages)][-1])    # "answer 5"
```

Token counts come from `approximate_tokens` (about four characters per token); pass
`estimator=` (a function from `Message` to `int`) to use a real tokenizer. The newest turn
is always kept, even when it alone exceeds the budget.

## Expiry and deletion

`default_ttl_seconds` on the store (or `ttl_seconds` per `create`) sets how long a
session lives without a save; each save moves the expiry forward. An expired session is
invisible immediately (`SessionNotFound`); `purge_expired()` reclaims its storage.
`delete(session_id, auth)` removes a session now and returns whether anything of that
owner's was deleted. Without a TTL, sessions are kept until deleted.

## What is stored, and personal data

Messages are stored with all their content parts: text, tool calls and tool results
(`ToolCallPart` / `ToolResultPart`), and images and documents (`ImagePart` /
`DocumentPart` — inline bytes as base64, URLs as given), so a stored tool conversation
replays exactly. The stored format is versioned and has a codec registry
(`register_part_codec`) for further part types; a stored part of an unknown type is
refused with `SessionFormatError` rather than dropped. `Extractor.extract(...,
session=...)` stores only the turn's text, with the number of attachments in the
message metadata — not the attachments themselves.

A store keeps, per session: every message exactly as given, each tool's state (the
extraction tool stores the values it extracted), the session metadata, the owner's
identity string, and the timestamps. **Raw user text can contain personal data**, and is
stored as-is by default.

A store takes an optional `sanitizer`: a function applied to every message on save,
whose result is what gets stored. `sanitize_message` masks e-mail addresses, tokens, IP
addresses, card numbers, national ids and phone numbers in text, using the same rules as
the rest of kuhaku:

```python
from kuhaku.core.auth import AuthContext
from kuhaku.core.models import Message
from kuhaku.core.session import InMemorySessionStore, sanitize_message

store = InMemorySessionStore(sanitizer=sanitize_message)
alice = AuthContext("alice", is_authenticated=True)
session = store.create(alice)
session.append(Message.user("write to me at someone@example.com"))
store.save(session, alice)
print(session.messages[0].text)        # "write to me at [EMAIL]"
```

`sanitize_message` also masks the content of tool results (`ToolResultPart`); tool-call
arguments and image/document bytes pass through unchanged. The sanitizer does not touch
tool state or metadata. Whether a sanitizer is required,
and which, is your deployment's decision; kuhaku does not enable one for you.

Logs and spans carry the `session_id` of the session involved (only ever a store-minted
id), never message content.

## Not yet available

- **RAG follow-up questions.** `RAG.ask` / `RAGEngine.answer` do not take a session. The
  RAG prompt path has no place for conversation history: the query-answer cache key, the
  input guard and the framework-owned system prompt are all built around one standalone
  question, so adding history is a change to each of them, not an extra parameter.
- **Async** store methods.
